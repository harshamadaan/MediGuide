# Medical Chatbot with RAG

This project is a medical question-answering chatbot built with a Retrieval-Augmented Generation (RAG) pipeline. Instead of asking the language model to answer from its own internal memory alone, the app first searches a local knowledge base of medical PDFs, retrieves the most relevant text chunks, and then asks the LLM to answer using that context.

The result is a chatbot that is more grounded in your source documents, easier to update, and much better suited for domain-specific answers than a plain prompt-only assistant.

## What the project does

The app lets you type a question in a Streamlit chat interface and receive an answer generated by Groq-hosted LLMs. Behind the scenes it:

1. Loads preprocessed document chunks from a FAISS vector store.
2. Embeds the user question with the same embedding model used during indexing.
3. Searches the vector store for the most similar chunks.
4. Passes those chunks to the LLM as context.
5. Returns a final answer in chat form.

This workflow keeps the model focused on the stored medical content instead of depending only on general model knowledge.

## Core concepts

### Retrieval-Augmented Generation (RAG)

RAG combines two stages:

- Retrieval: find the most relevant pieces of your knowledge base.
- Generation: ask an LLM to answer using the retrieved context.

In this project, the retrieval step happens through FAISS, which stores vector embeddings of the document chunks. The generation step happens through a Groq chat model.

### Chunking

Before documents can be searched effectively, they are split into smaller pieces called chunks. This project uses RecursiveCharacterTextSplitter with:

- chunk_size = 500
- chunk_overlap = 50

That means each chunk is approximately 500 characters long, and consecutive chunks overlap by 50 characters. The overlap helps preserve context across boundaries so important sentences are not cut off too aggressively.

Chunking matters because large documents are too broad for reliable retrieval. Smaller chunks make it easier to locate the exact passage that answers a question, while overlap reduces the chance of losing meaning between sections.

### Embeddings

Embeddings are numeric representations of text. Similar meanings end up with vectors that are close together in vector space.

This project uses sentence-transformers/all-MiniLM-L6-v2 through HuggingFaceEmbeddings. The same embedding model is used when:

- building the vector store from the PDF chunks
- encoding the user query at runtime

Using the same embedding model on both sides is important, because retrieval only works properly when documents and queries live in the same vector space.

### FAISS vector store

FAISS is a fast similarity-search library. Here it is used to store document embeddings locally under vectorstore/db_faiss.

At query time, the app converts the user question into an embedding and asks FAISS for the nearest matches. The app currently retrieves the top k = 3 chunks, which are then inserted into the prompt sent to the LLM.

### Prompting and answer generation

The answer is generated through a LangChain retrieval chain. The app pulls the standard retrieval-qa-chat prompt from LangChain Hub and combines it with the retrieved chunks using create_stuff_documents_chain.

That means the model receives:

- the user’s question
- the top matching context chunks
- a prompt structure designed for retrieval QA

The model used in the Streamlit app is llama-3.1-8b-instant through Groq, with temperature=0.5 for a balance between stability and flexibility.

## Project flow

The repository has two helper scripts plus the Streamlit UI:

### 1. Create the memory / vector store

create_memory_for_llm.py loads PDF files from the data/ folder, splits them into chunks, embeds them, and saves the resulting FAISS index to vectorstore/db_faiss.

This is the indexing step. You run it when:

- you add new PDFs
- you change the chunking logic
- you want to rebuild the local knowledge base from scratch

### 2. Connect the memory with the LLM

connect_memory_with_llm.py is a simple command-line version of the RAG workflow. It loads the same FAISS index, asks the Groq model a single user query from the terminal, and prints the answer plus the retrieved document metadata.

This script is useful for quick debugging because it shows whether retrieval is working before you open the Streamlit app.

### 3. Run the Streamlit chatbot

medibot.py is the user-facing application. It loads the FAISS index, accepts chat input, stores conversation messages in Streamlit session state, and displays answers in a chat-style interface.

## How the RAG pipeline works in this codebase

The runtime flow is straightforward:

1. The user enters a question in the Streamlit chat box.
2. The app loads the vector store from vectorstore/db_faiss.
3. The question is embedded using sentence-transformers/all-MiniLM-L6-v2.
4. FAISS returns the three most similar chunks.
5. The retrieval prompt combines the question and the chunks.
6. Groq’s llama-3.1-8b-instant model generates the final answer.
7. The response is shown in the chat UI and stored in session history.

This is the key design idea of RAG: the language model does not need to guess from memory when the answer is likely present in your documents.

## Why chunking is important here

Medical PDFs often contain long sections, tables, and dense explanations. If you embed entire pages as one block, the retrieval step becomes less precise. The model may receive too much irrelevant content or miss the exact sentence that matters.

Chunking solves that by breaking documents into smaller semantic units:

- retrieval becomes more precise
- irrelevant content is reduced
- the model gets only the best matching context
- overlap preserves continuity across chunk boundaries

The current 500/50 settings are a practical starting point. Smaller chunks usually improve precision, while larger chunks can preserve more context. The overlap helps balance both.

## Environment setup

The project uses uv for environment management and dependency installation.

### Create a virtual environment

```powershell
uv venv --python "C:\Users\Hp\AppData\Local\Programs\Python\Python311\python.exe"
```

### Activate the environment

```powershell
.\.venv\Scripts\Activate.ps1
```

### Install dependencies

```powershell
uv pip install -r requirements.txt
```

## Run the project

### Step 1: Build the vector store from PDFs

```powershell
uv run create_memory_for_llm.py
```

This command reads PDF files from data/, splits them into chunks, embeds them, and writes the FAISS index into vectorstore/db_faiss.

### Step 2: Test retrieval from the command line

```powershell
uv run connect_memory_with_llm.py
```

This is a useful smoke test. If this works, it usually means your embeddings, FAISS index, and Groq key are set correctly.

### Step 3: Launch the Streamlit UI

```powershell
uv run streamlit run medibot.py
```

This starts the web interface where you can ask medical questions interactively.

### Optional: Run the app module directly

```powershell
uv run medibot.py
```

This project also exposes the app through the Python entrypoint defined in pyproject.toml, which is why the package can be launched as a module as well.

## Configuration

The app uses environment variables loaded through python-dotenv.

### Required

- GROQ_API_KEY: required for the Groq chat model.

### Optional or situational

- HF_TOKEN: loaded by the code, but not currently passed into the embedding loader. It may still be useful if you later switch to a Hugging Face resource that requires authentication.

If the key is missing, the app will fail when it tries to call Groq.

## Repository layout

- data/: source PDF documents used to build the knowledge base.
- vectorstore/db_faiss/: persisted FAISS index for retrieval.
- create_memory_for_llm.py: builds the vector store from PDFs.
- connect_memory_with_llm.py: terminal-based RAG test script.
- medibot.py: Streamlit chat application.
- src/medical_chatbot_with_rag/: package entrypoint support.

## Practical notes

- Rebuild the vector store whenever the PDFs in data/ change.
- Keep the embedding model consistent between indexing and querying.
- The answers are only as good as the retrieved chunks, so document quality matters a lot.
- This project is designed for informational assistance and retrieval from source documents, not for replacing professional medical judgment.

## Troubleshooting

### The app says the vector store cannot be loaded

Check that vectorstore/db_faiss exists and that create_memory_for_llm.py has been run successfully.

### The model call fails

Check whether GROQ_API_KEY is set in your environment or .env file.

### Retrieval looks wrong or incomplete

Rebuild the index after confirming the PDFs were placed in data/, then rerun the command-line script to verify the retrieved context.

### Streamlit does not open

Make sure you are running the command from the project root and that the virtual environment has the project dependencies installed.

## Summary

This repository implements a compact but complete RAG chatbot pipeline:

- PDF ingestion
- chunking with overlap
- Hugging Face embeddings
- FAISS similarity search
- Groq-powered response generation
- Streamlit chat UI

The design keeps the knowledge base local and the LLM responses grounded in your documents, which is the main advantage of the RAG approach.
